# Задача: реальные описания и фото для всех 76 записей (4 датасета)

**Исполнитель:** Antigravity
**Роль:** Data agent.
**Тип:** сбор данных, объём большой (76 записей, 4 CSV-файла) — сопоставим по масштабу с уже сделанными `antigravity-geocode-listings`/`antigravity-collect-grooming-prices`.
**Ветка:** `antigravity/collect-descriptions-and-photos`
**Зависимости:** нет. `tasks/cli-integrate-descriptions-and-photos.md` (CLI) зависит от этой — начинается после её мерджа.

## Контекст

Редизайн сайта (PR #38-41, смёржены) уже построил UI под фото-галерею и
короткое описание на карточке/странице бизнеса — но сейчас показывать
нечего: у всех 76 бизнесов `photoUrls` пуст, а `Business.notes` (то,
что временно пытались показывать как описание) оказалось служебными
пометками сборщика данных ("docs/concept.md absent; district omitted
per instructions" и т.п.), не текстом для посетителей — это разбирал
Claude Code CLI в PR #40, открытый вопрос оттуда закрывает эта задача.

**Единый формат хранения (решение облачного Claude Code, чтобы не
изобретать на ходу):** данные остаются в уже существующем пайплайне
`data/*.csv` → `seed.ts` → БД, не отдельным хранилищем. В каждый из 4
файлов (`data/salons-bratislava.csv`, `data/vet-clinics-bratislava.csv`,
`data/pet-hotels-bratislava.csv`, `data/other-pet-services-bratislava.csv`)
добавляются **два новых столбца** в конец (после существующих, чтобы
не сдвигать текущие):
- `description` — короткий текст на английском, 1-3 предложения.
- `photo_urls` — прямые ссылки на изображения, через `;` (тот же
  формат, что уже использует столбец `animals`, например
  `https://site.sk/img/1.jpg;https://site.sk/img/2.jpg`).

Оба столбца могут быть пустыми для конкретной строки — это ожидаемо,
не ошибка (тот же принцип «нет данных → нет блока», что и везде в
проекте).

## Что сделать

1. **Описание (`description`):** для каждого бизнеса — короткий
   текст на английском, только из проверяемых фактов:
   - Если на официальном сайте бизнеса (тот же `website`, что уже в
     CSV) есть текст о себе (раздел "About"/главная страница) —
     адаптировать на английский коротко (не дословный юридический
     перевод, естественный текст для посетителя каталога, но без
     добавления фактов, которых нет в оригинале).
   - Если официального текста о себе нет — короткая фактическая фраза
     из уже известных полей (категория, район, виды животных,
     специализация из `notes`, если она там реально есть, а не
     служебный мусор) — например «Dog grooming salon in Ružinov,
     offering trims, baths and nail care.» Без превосходных степеней
     и маркетинговых утверждений («лучший», «топовый»), которых нет в
     источнике.
   - Если ни того, ни другого нет — оставить `description` пустым, не
     сочинять.
2. **Фото (`photo_urls`):** только прямые ссылки на изображения,
   размещённые **на собственном официальном сайте бизнеса** (домен
   должен соответствовать/относиться к значению `website` в той же
   строке). 1-4 фото на бизнес достаточно, не нужно выкачивать всю
   галерею сайта.
   - **Категорически нельзя:** Google Maps/Google Business Profile,
     Facebook/Instagram (даже открытые публичные страницы), TripAdvisor,
     другие агрегаторы/каталоги, стоковые фото — это прямо запрещено
     правилами проекта (см. `docs/design-plan.md` раздел 2.1: «фото
     салонов без разрешения не использовать», единственное
     согласованное исключение — фото, которые сам бизнес публикует на
     собственном сайте).
   - Если у бизнеса нет официального сайта, или на сайте нет фото —
     `photo_urls` пустой. Не подставлять никакую замену.
3. **Отзывы — НЕ собирать, это вне объёма задачи.** Решение
   облачного Claude Code: отзывы на Pawenn по архитектуре сайта — это
   уже сделанная форма `/api/reviews`, куда реальные посетители сами
   оставляют отзыв (создаётся `Review` со статусом `PENDING`,
   модерация вручную). Копировать отзывы с Google/Facebook и
   показывать их как будто это отзывы, оставленные на Pawenn, —
   (а) не соответствует действительности (это чужие отзывы, оставленные
   не здесь), (б) вероятно нарушает условия использования тех
   платформ, (в) прямо противоречит уже принятому дизайну модели
   `Review`. Эта часть исходного запроса сознательно не идёт в задачу.

## Definition of Done

- Все 4 CSV-файла в `data/` получили столбцы `description` и
  `photo_urls` (пустые значения допустимы, где реально нечего указать).
- Ни одного выдуманного факта в `description`, ни одной ссылки на фото
  не с официального сайта бизнеса в `photo_urls`.
- PR открыт в `main`, в описании — краткая сводка (сколько записей
  получили описание/фото, сколько осталось пустыми и почему в общих
  чертах, если есть явная причина типа «у бизнеса нет сайта»).

## Если что-то неясно

Не додумывать факты о бизнесах. Если для конкретной записи неясно,
можно ли использовать найденное фото (домен не совпадает с `website`
явно, но похож — поддомен, редирект и т.п.) — пропустить эту запись,
не гадать, отметить в PR как пропущенную с причиной.
