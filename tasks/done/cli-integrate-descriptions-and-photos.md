> **Закрыта 2026-09-26 («левая рука», по указанию владельца).** Описания сделаны (`description`, `description_local` у всех 76 мест). Фото отменены решением владельца (2026-09-25): чужие фото по ссылкам не показываем и сгенерированные не делаем, в карточке логотип.


> **Частично сделано (2026-09-24, облачный Claude Code, «правая рука»):**
> `Business.description` добавлен в схему и seed вместе с полями
> карточки (миграция `listing_card_data`), текст показывается на
> странице места. **Осталось только фото:** `photo_urls` в seed не
> загружаются сознательно. Это ссылки на чужие сайты (могут сломаться,
> вопрос прав), и владелец решил, что в карточке будет логотип, а не
> фото. Перед показом фото на странице места нужно решение владельца.

**Исполнитель:** Claude Code CLI (локальный)
**Роль:** Builder agent.
**Тип:** миграция схемы БД (против реальной продакшен-базы) + интеграция данных, объём небольшой/средний.
**Ветка:** `cli/integrate-descriptions-and-photos`
**Зависимости:** требует смёрженную `antigravity-collect-descriptions-and-photos` — без новых столбцов `description`/`photo_urls` в `data/*.csv` делать нечего. Схема БД — CLI-only по правилу в `AGENTS.md` («важные/высокоуязвимые задачи» — миграции против настоящей базы).

## Контекст

`Business.notes` — служебные пометки сборщика, не текст для
посетителей (разобрано в PR #40). `Antigravity` (соседняя задача)
собрала настоящие описания и ссылки на фото в новые столбцы CSV
`description`/`photo_urls` (`;`-разделённый список, как `animals`).
Эта задача — довести их до сайта.

## Что сделать

1. **Схема** (`website/prisma/schema.prisma`): добавить
   `Business.description String?` — отдельное от `notes` поле,
   `notes` не трогать и не удалять (остаётся внутренним служебным
   полем, как и было). `photoUrls String[]` уже существует, менять не
   нужно.
2. **`prisma/seed.ts`:** читать новые колонки `description` и
   `photo_urls` (split по `;`, обрезать пробелы, отбросить пустые
   элементы — тот же паттерн, что уже есть для `animals`), прокинуть
   в `business.upsert()` — **и в `update`, и в `create`** блоки (текущий
   апсерт уже обновляет существующие строки при повторном запуске по
   `slug`, значит просто добавить туда оба поля — ничего chinить в
   самой механике upsert не требуется).
3. **`lib/data.ts`:** `publicDescription()` (введена в PR #40 как
   обходной фильтр `notes`) — заменить на прямое чтение
   `business.description`, саму функцию-фильтр удалить, если она
   после этого больше нигде не используется. Проверить оба места
   использования (`BusinessCard.tsx`, `app/business/[slug]/page.tsx`)
   — просто переключить источник, вёрстку не трогать (она уже
   рассчитана на «нет данных → нет блока», значит `description: null`
   ведёт себя как и раньше `publicDescription() === null`).
4. **Миграция и сид против реальной БД:** `npx prisma migrate dev`,
   затем `npm run db:seed` — прогнать по-настоящему (не только
   написать), проверить в PR, что реальные `description`/`photoUrls`
   реально записались (например, count непустых значений до/после).
5. **Фото — учесть хотлинк-риск:** `photoUrls` теперь содержат прямые
   ссылки на чужие домены (официальные сайты бизнесов). Некоторые
   сайты блокируют хотлинк по `Referer`/CORS — картинка может не
   загрузиться в `<img>`. Компонент `PhotoGallery` уже показывает
   аккуратную заглушку, когда `photoUrls` пуст — использовать тот же
   fallback-паттерн (`onError` на `<img>`, переключение на заглушку),
   если изображение реально не грузится, а не оставлять сломанную
   иконку браузера.

## Definition of Done

- `Business.description` в схеме, применена миграция против реальной БД.
- `seed.ts` заполняет `description`/`photoUrls` из новых колонок CSV, реально прогнан.
- Карточка бизнеса и страница бизнеса показывают настоящее описание/фото там, где они есть в данных, и корректно ничего не показывают там, где их нет (включая fallback при недогрузке хотлинкнутой картинки).
- `npm run build` и `npm run lint` проходят.
- Проверено в браузере (Playwright MCP) минимум на одном бизнесе с реальными фото/описанием и одном без.
- PR открыт в `main`.

## Если что-то неясно

Технические детали (как именно фильтровать пустые элементы `photo_urls`, куда класть `onError`-фолбэк) — на усмотрение исполнителя. Если после интеграции окажется, что многие хотлинки не грузятся из-за защиты сайтов — не подключать платный пайплайн загрузки/перехостинга фото самостоятельно (это отдельное решение с возможными расходами), написать об этом в PR как открытый вопрос.
