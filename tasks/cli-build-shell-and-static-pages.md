# Задача: шапка/подвал, статические страницы, sitemap, рабочий поиск с главной

**Исполнитель:** Claude Code CLI (локальный)
**Роль:** Builder agent.
**Тип:** новые страницы + доработка существующих, объём средний.
**Ветка:** `cli/build-shell-and-static-pages`
**Зависимости:** формально не требует смёрженной
`cli-generalize-business-model-and-seed` — можно начинать сразу,
`website/` уже в `main` (Next.js-scaffold с CSV-версией `lib/data.ts`),
этого достаточно для всех пунктов этой задачи, кроме реальных
счётчиков на главной (см. пункт 2 ниже — там явно расписано, что
делать, пока `Business`/Prisma ещё не готовы). Может идти параллельно
с `cli-build-listing-and-detail-pages` (разные файлы: эта задача не
трогает `website/app/[category]/...` и `website/app/business/...`),
но лучше синхронизироваться, если работаете одновременно, чтобы не
разъехаться в компоненте `Header`/`Footer`.

**Обновление 2026-09-21 (владелец проекта):** эта задача была на
короткое время переназначена на Antigravity, затем возвращена
обратно CLI — решение владельца: весь фронтенд/внешний вид сайта
делает только Claude Code CLI, потому что только у него есть
возможность локально поднять сайт и визуально проверить результат
(например, через Playwright MCP, см. `AGENTS.md`); у Antigravity
такой возможности нет, визуальные задачи у неё выходят «криво-косо»
без способа это проверить. См. новое правило в `AGENTS.md` — раздел
«Распределение задач между агентами».

## Контекст

Описание блоков — `docs/design-plan.md`, разделы 4.1, 4.5-4.7, 5.

## Что сделать

1. **Header/Footer** (`website/components/Header.tsx`, `Footer.tsx` или где принято в проекте): ссылки на все 6 категорий по городу (сейчас фактически `/grooming/bratislava/`, `/vet-clinics/bratislava/` и т.д.), ссылка на `/how-it-works/`, в футере — доп. ссылки на Privacy/Terms. Слаг города в этих ссылках брать из данных (например, «основной»/первый `City` из БД или константа `DEFAULT_CITY_SLUG` в одном месте), а не хардкодить `bratislava` в каждой ссылке по отдельности — см. `docs/design-plan.md` раздел 2.2 про динамический `[city]`, чтобы при добавлении следующего города не пришлось руками находить и менять все вхождения строки.
1a. **Логотип (финально утверждён владельцем 2026-09-21):** использовать `design/logo-concepts/13-duo-puppy-ears.svg` (иконка + двухцветный wordmark «Paw»/«enn») как логотип сайта в Header — вместо текущего текстового placeholder «pawenn» в `website/app/layout.tsx`. Собрать из значка (без текста, только `<g>` с мордочкой) отдельный favicon: сконвертировать `design/logo-concepts/13-duo-puppy-ears-favicon.svg` в `website/app/favicon.ico` (растеризация, любой доступный инструмент — `sharp`, `svg2ico`, онлайн-конвертер вручную и т.д., на усмотрение исполнителя), заменив текущий дефолтный Next.js favicon. См. `design/logo-concepts/README.md` (раздел «Финальный выбор») — там же кратко описана история решения.
2. **Главная страница** (`website/app/page.tsx`):
   - Подключить реальный сабмит поиска: и мобильные карточки-шаги, и десктопная строка при выборе/сабмите должны редиректить на `/{category}/{city}/?district=...&animal=...`, где `{city}` — тот же источник (переменная/константа), что и в Header/Footer выше, не отдельно захардкоженный `bratislava` (конкретную реализацию редиректа — client-side `useRouter().push(...)` или обычная форма с `GET` — на усмотрение исполнителя).
   - Мобильные шаги 2-3 (услуга/район) — по явному запросу владельца открывать как полноэкранный оверлей с фокусом на выборе и списком популярных вариантов (референс Zocdoc mobile, разобран в `docs/design-plan.md` раздел 4.1 и `docs/research/interface-references.md` раздел 1.1), а не просто разворачивать плоский список карточек на месте, как сейчас.
   - Счётчики (`getBusinessCount`) — после того как `lib/data.ts` переведён на Prisma Client (см. соседнюю задачу `cli-build-listing-and-detail-pages` — если она уже смёржена, использовать её версию `lib/data.ts`; если ещё нет, не дублировать работу — согласовать порядок, или временно оставить CSV-версию и explicitly отметить в PR, что счётчики будут актуализированы после мерджа той задачи).
   - Добавить блок «как это работает» (короткий тизер + ссылка на `/how-it-works/`).
3. **Статические страницы:**
   - `/how-it-works/` — рендерит `docs/content/how-it-works-draft.md` (можно через простой Markdown-рендерер, например `react-markdown`, или руками перенести в JSX — на усмотрение исполнителя, главное не терять текст и сохранить плашку `DRAFT`).
   - `/privacy-policy/` — рендерит `docs/legal/privacy-policy-draft.md`, метатег `noindex` (плейсхолдеры `{OPERATOR}` и т.д. ещё не заполнены владельцем).
   - `/terms-of-use/` — аналогично `docs/legal/terms-of-use-draft.md`, тоже `noindex`.
   - `/add-or-fix-listing/` — простая страница с `mailto:`-ссылкой (без формы и бэкенда в этой задаче — форма с реальной отправкой не входит в объём MVP этой задачи).
4. **`sitemap.xml`/`robots.txt`:** использовать `website/app/sitemap.ts`/`robots.ts` (нативная поддержка Next.js App Router). Sitemap должен исключать любые страницы с `noindex` (категории/районы с < 3 бизнесами, privacy/terms).
5. **Правка `DESIGN.md`** (корень репозитория, не `website/DESIGN.md`): убрать раздел «Accessibility Baseline» (WCAG 2.1 AA) целиком — владелец проекта явно отказался от accessibility-требований (см. историю правок `PRODUCT.md`), и этот раздел ему противоречит. Не заменять его никаким другим требованием — просто убрать, это осознанное решение владельца, не наше дело компенсировать.

## Критерии готовности (Definition of Done)

- Header/Footer видны на всех страницах сайта, ссылки рабочие.
- Header использует финальный логотип (`design/logo-concepts/13-duo-puppy-ears.svg`), `website/app/favicon.ico` заменён на растеризованную версию значка (не дефолтная иконка Next.js).
- Поиск с главной страницы реально переводит на страницу категории с примененными query-параметрами.
- `/how-it-works/`, `/privacy-policy/`, `/terms-of-use/`, `/add-or-fix-listing/` открываются и показывают контент из соответствующих `docs/`-файлов.
- `sitemap.xml` и `robots.txt` генерируются и не содержат `noindex`-страниц.
- `DESIGN.md` больше не содержит требования WCAG 2.1 AA.
- `npm run build` и `npm run lint` проходят.
- PR открыт в `main`.
