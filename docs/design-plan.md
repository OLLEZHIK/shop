# Design-план: страницы, компоненты, URL

**Статус:** рабочий план для реализации, не финальный визуальный макет.
Опирается на `PRODUCT.md`, `docs/concept.md` (разделы 4-5, 8),
`docs/ux-flow.md` и на уже существующий черновик `DESIGN.md` (создан
Claude Code CLI на ветке `cli/initial-website`, ещё не смёржен).
Задача этого файла — свести всё в одну карту «какие страницы есть,
что на них, какой URL» и разложить это на конкретные задачи в
`tasks/` для исполнителей.

**Что уже реализовано на ветке `cli/initial-website` (не смёржена,
ждёт PR):** Next.js 16 + Tailwind 4 + Prisma 8-rc, главная страница с
3-шаговым флоу и десктопной строкой поиска (`website/app/page.tsx`),
черновая Prisma-схема только с моделью `Salon` (только груминг),
`website/lib/data.ts` — читает 4 CSV напрямую в рантайме наивным
парсером (**баг: `line.split(',')` ломается на адресах с запятой в
кавычках**, например `"Ružinovská 1/4814, 821 02 Bratislava"` — это
надо исправить, не повторять). Ниже — план, который достраивает это
до полноценного набора страниц.

## 1. Дизайн-система (токены)

Берём как есть из `DESIGN.md` (палитра, типографика, отступы, сетка,
анимации, бюджет производительности) — там всё разумно и совпадает с
`PRODUCT.md`. **Одно расхождение, которое нужно поправить**: раздел
`DESIGN.md` → «Accessibility Baseline» требует WCAG 2.1 AA — это прямо
противоречит явному решению владельца проекта убрать accessibility из
требований (см. `PRODUCT.md`, история изменений). Это техдолг для
задачи `cli-build-shell-and-static-pages` — убрать раздел, не заменяя
его ничем (не наша обязанность, но и не наше дело её выдумывать).

Ключевое, что использую дальше как факт:
- Цвета: `brand-orange #FF6B35`, `brand-blue #004E89`, `success #06A77D`, фон `#F7F9FB`.
- Шрифт: Inter (заголовки/текст/UI), моноширинный для телефонов/адресов — опционально, не критично для MVP.
- Референс интерфейса: TripAdvisor (карточки/списки) + Zocdoc (комбинированная строка поиска на десктопе).

**Обновление 2026-09-22 (владелец): редизайн визуального языка.**
MVP-версия (описанная выше и в разделах 4-5) оказалась функционально
корректной, но визуально «дефолтной» — потому что задачи на неё
описывали контент/поведение, а не художественный язык, и ссылались на
`DESIGN.md` как на готовый источник, хотя он сам был черновиком из
первого скелета проекта. Владелец прислал детальное ТЗ на редизайн
(референс — по-прежнему Zocdoc, но с более выразительным языком:
ambient-градиенты/блёрные пятна в брендовых цветах на молочном фоне,
геометричный гротеск для заголовков — выбран **Plus Jakarta Sans**,
безрамочный хедер с pill-hover, кликабельные карточки с фото-галереей
и подъёмом на hover, карта, блок «похожие рядом»). Разложено на 4
задачи (раздел 7 ниже, `cli-redesign-*`), с единым файлом
дизайн-токенов (`website/app/design-tokens.css`) как основой — чтобы
дальнейшие эксперименты с цветом/шрифтом не требовали правок по всему
коду. Принципы данных (не выдумывать факты/партнёров/статистику,
блоки без данных не рендерятся) — те же, что и везде в проекте,
явно прописаны в каждой из четырёх задач.

## 2. Данные: от «только Salon» к «4 категориям»

Текущая Prisma-схема (`website/prisma/schema.prisma`) моделирует
только груминг-салоны. Но `data/` уже содержит 4 категории (76 строк
суммарно): `salons` (груминг), `vet-clinics`, `pet-hotels`,
`other-pet-services` (там ещё 3 подкатегории: `shop`, `training`,
`sitting`). Раз данные уже шире груминга — схема должна это отражать
**до** того, как строить страницы поверх неё, иначе придётся
переделывать дважды.

**Решение (архитектурное, в рамках задачи по данным — не требует
уточнения у владельца, см. AGENTS.md, принцип автономности):**
переименовать `Salon` → `Business` с полем `category`:

```prisma
enum BusinessCategory {
  GROOMING
  VET_CLINIC
  PET_HOTEL
  PET_SHOP
  DOG_TRAINING
  PET_SITTING
}
```

Остальные поля модели остаются как в текущей схеме (address, phone,
email, website, animals[], specialties[]/notes, status, featured,
verifiedAt, sourceUrls[], lat/lng — пока nullable, districtId —
nullable, пока не докончен `cli-backfill-districts-all-datasets`).
`Service`/`PriceItem` остаются отдельными таблицами (одна связь
`Business -> PriceItem[]`) — цена не обязана быть у каждого бизнеса
сразу (см. раздел 4 ниже про цены).

Подробности реализации — в `tasks/cli-generalize-business-model-and-seed.md`.

### 2.1 Отзывы, рейтинг и фото — решение владельца, переносим из P1 в MVP

`docs/concept.md` (раздел 8) изначально откладывал отзывы на потом
(«Без отзывов в MVP»). Владелец проекта явно попросил включить это в
основной флоу сейчас — фиксирую это как решение и обновляю объём:

- **Отзывы только настоящие, от реальных пользователей** — принцип «не
  выдумывать факты о бизнесах» (`PRODUCT.md`) остаётся в силе. Никаких
  сгенерированных или перенесённых с других сайтов отзывов.
- Новая модель `Review` (`businessId`, `authorName`, `rating` 1-5,
  `comment`, `status: PENDING | PUBLISHED | REJECTED`, `createdAt`).
  По умолчанию `PENDING` — обычная форма без подтверждения email в
  MVP может собрать спам/мусор, поэтому публикация не автоматическая.
  Модерация в этой итерации — вручную через Prisma Studio/прямой
  запрос к БД (полноценная админка для этого — отдельная будущая
  задача, не в объёме текущих задач).
- Рейтинг на карточке и на странице бизнеса — среднее только по
  `PUBLISHED` отзывам. Если опубликованных отзывов нет — рейтинг не
  показываем вообще (не «0.0», а просто нет бейджа), это тот же принцип,
  что и с ценами (см. раздел 4.4 ниже).
- **Фото** — добавляем поле `photoUrls: String[]` на `Business`, но
  учитываем ограничение из `docs/concept.md` (раздел 12): «фото
  салонов без разрешения не использовать». Для MVP это значит: пусто,
  пока не появится либо (а) фото, которые сам бизнес публикует на
  собственном сайте (с указанием источника), либо (б) полноценный
  пайплайн загрузки фото с правами — вторая задача на будущее. Не
  подключаем сюда чужие фото с Google Maps/агрегаторов — это прямо
  запрещено правилами проекта.

**Обновление 2026-09-23:** вариант (а) выше — в работе. Новая задача
`tasks/antigravity-collect-descriptions-and-photos.md` собирает
реальные фото (только хотлинк на официальный сайт бизнеса, домен
должен совпадать с полем `website`) и настоящие короткие описания —
двумя новыми столбцами (`description`, `photo_urls`, `;`-разделитель
как у `animals`) прямо в существующих `data/*.csv`, без новой
инфраструктуры хранения. `Business.notes` при этом остаётся
внутренним служебным полем (не текстом для посетителей — см. разбор в
PR #40) и не смешивается с новым `description`. Интеграция в схему/seed
— `tasks/done/cli-integrate-descriptions-and-photos.md` (миграция против
реальной БД, поэтому CLI, не Antigravity — см. `AGENTS.md`).
**Отзывы по-прежнему только первого лица через `/api/reviews`** — не
переносятся с других платформ ни при каких обстоятельствах, это не
пересматривается.

Реализация вью (карточка, форма отзыва, галерея) — в
`tasks/cli-build-listing-and-detail-pages.md`, схема — в
`tasks/cli-generalize-business-model-and-seed.md`.

### 2.2 Мультигород/мультистрана: как масштабироваться без переписывания кода

> **Обновление 2026-09-23 (владелец) — отменяет пункт ниже про
> «интерфейс всегда английский».** У каждой страницы теперь есть полная
> версия на языке города: английский без префикса (`/grooming/bratislava/`),
> местный язык с префиксом (`/sk/psi-salon/bratislava/`), обе связаны
> hreflang (canonical на себя, `x-default` — английская). Реализация:
> `website/proxy.ts` (переписывает адреса без префикса на `app/[lang]`),
> `website/lib/i18n.ts` (словари UI, язык страны — `COUNTRY_LANGUAGE`),
> `website/lib/categories.ts` (слаги и названия по языкам),
> `website/lib/seo.ts` (hreflang), sitemap с `xhtml:link`. Новый город в
> уже поддерживаемой стране — только данные. Новый язык — один словарь
> и набор слагов. Страницы Help и юридические пока только на английском.
> Словацкие слаги живые с v2; менять их только при явной разнице в спросе
> (`docs/seo/keywords/`, `tasks/antigravity-keywords-sk.md`).

Решение владельца (2026-09-21): в будущем новые города добавляются
как данные, а не как задача на разработку — «настроили один раз,
дальше только добавление городов». **Отменяет** прежний план
`docs/concept.md` раздел 4 про `/sk/` вторым языком + hreflang —
вместо параллельных языковых версий одной страницы теперь одна
страница на город, язык контента определяется городом.

Чтобы это реально работало без правок кода на каждый новый город,
закладываем сейчас (пока `website/` ещё не существует в `main` — самый
дешёвый момент менять схему):

- **`City` получает поля `country` и `locale`** (BCP-47, например `sk`,
  `cs`) — язык страницы города определяется по этим данным
  автоматически, руками не назначается. Опционально `localizedName`,
  если название города отличается в разных языках (Vienna/Wien) — не
  критично для MVP с одним городом.
- **Роутинг — по динамическому сегменту `[city]`, не по литеральной
  папке.** Черновик задачи `cli-build-listing-and-detail-pages`
  изначально описывал `app/[category]/bratislava/page.tsx` — это
  ловушка: жёстко зашитое имя города требует нового кода и деплоя на
  каждый следующий город. Должно быть `app/[category]/[city]/page.tsx`
  с `generateStaticParams`, читающим список городов из БД.
- **Текст страницы — из словаря «категория × язык», не пишется заново
  на город.** Название города — просто данные, подставляются в текст.
  Переводить нужно один раз на язык (6 названий категорий + пара
  фраз-шаблонов вроде «Find {category} in {city}»), а не один раз на
  город — это и есть ключевой момент масштабирования: трудозатраты
  растут с числом языков, а не с числом городов.
- **Интерфейс (не текст страницы, а UI: кнопки, фильтры, форма отзыва,
  навигация, футер, юридические страницы) остаётся английским всегда**,
  для любого города/страны — никакой отдельной i18n-инфраструктуры
  для интерфейса не заводим, это не масштабируется на десятки языков
  вручную.
- **Индексация — уже работает через существующее `noindex`-правило**
  (раздел 3 ниже): как только `sitemap.ts` читает данные из БД
  динамически, новый город сам попадает в sitemap, как только
  пересекает порог в 3 опубликованных бизнеса — без ручных действий.
  Нужна on-demand ревалидация (`revalidatePath`/ISR) при добавлении
  бизнеса или города, чтобы страница ожила без пересборки. Дальше
  Google находит и индексирует по sitemap на своём расписании — это
  нормально, специально ускорять (пинг Search Console/IndexNow) не
  обязательно.
- Первые страницы (Братислава) можно и нужно делать сейчас на
  английском (`City.locale = "en"` для Братиславы на старте) — ничего
  не теряется, просто схема с самого начала готова к тому, что
  следующий город придёт с другим `locale` и не потребует правок кода.

Подробности реализации схемы — `tasks/cli-generalize-business-model-and-seed.md`,
роутинга — `tasks/cli-build-listing-and-detail-pages.md`.

> **Языковая модель (владелец, 2026-09-23, окончательная). Отменяет
> схему «английский без префикса + `/sk/` для местного языка» из
> обновления в начале этого раздела.** Главное: почти все ищут на
> местном языке, поэтому всё про город — на языке города.
>
> 1. **Язык задаёт город.** Язык по умолчанию — язык страны города
>    (`COUNTRY_LANGUAGE`), у страны с несколькими языками — список
>    языков, первый — по умолчанию. Английский есть у каждого города
>    как дополнительная версия.
> 2. **Всё про город — на его языке:** интерфейс, карточки, описания,
>    FAQ, Help, юридические страницы, meta title/description, OG, тексты
>    ошибок, 404. На странице местного языка английский текст как
>    запасной вариант не подставляется: нет местного текста — нет блока.
>    На английской версии: английский текст, если он есть, иначе
>    местный. Названия и адреса заведений не переводятся.
> 3. **Префикс у каждого языка, включая английский:**
>    `/sk/psi-salon/bratislava/`, `/en/grooming/bratislava/`,
>    `/sk/podnik/{slug}/`, `/en/business/{slug}/`,
>    `/en/how-it-works/` (словацкие слаги — после
>    `docs/seo/keywords/`). Старые адреса без
>    префикса — 301 на `/en/...`. Каждая страница — self-canonical +
>    hreflang на все свои языковые версии, `x-default` — корень `/`.
> 4. **Выбор языка — только на корне `/`:** cookie с последним
>    выбранным языком → `Accept-Language` (если язык поддерживается) →
>    язык страны по IP (`x-vercel-ip-country`) → английский. Корень
>    делает временный (302/307) редирект, `Vary: Cookie, Accept-Language`.
>    Никакие другие адреса по cookie/браузеру не редиректят и не меняют
>    текст: у ботов нет cookie, каждая языковая версия индексируется по
>    своему URL.
> 5. **Переключатель языка** ведёт на ту же страницу на другом языке и
>    записывает выбор в cookie. Внутренние ссылки (Browse, геолокация
>    «ближайший город», поиск) ведут на текущий язык посетителя; если
>    у города нет этого языка — на язык города по умолчанию.
> 6. **Один домен** `pawenn.com`, языки — папками. Отдельные домены
>    (`pawenn.sk` и т.п.) — только если страна станет большой.
> 7. Контент заведений по языкам: в CSV `description` (английский) и
>    `description_<locale>`; новый язык — новый столбец, без правки схемы.
>
> Задачи: `tasks/cli-language-model-v2.md` (п. 1, 3-6),
> `tasks/antigravity-slovak-descriptions.md`,
> `tasks/done/cli-full-local-language-sk.md` (п. 7 — через `description_local`;
> п. 2 отменён: Help и юридические — только на английском, без пометки
> «(EN)», не переводятся; решение владельца 2026-09-26).

## 3. URL-структура (английская, подтверждена исследованием)

`docs/concept.md` (раздел 4) зафиксировал переход на английский
базовый язык, но explicitly оставил словацкие slug'и («не переводить
на глаз, нужно исследование ключевых слов»). Ниже — схема, которую я
зафиксировал как рабочую по принципу автономности, и которую затем
подтвердило исследование Antigravity
(`docs/seo/english-keywords.md`, задача
`tasks/antigravity-seo-english-keywords.md`, смёржено): 5 из 6 слагов
подтверждены как есть, один изменён по результатам исследования —
`pet-training` → `dog-training` (весь спрос англоязычных запросов на
эту категорию — про собак, ни одного примера с «pet training» или про
кошек; все 7 поставщиков в `data/other-pet-services-bratislava.csv`
— именно собачьи школы дрессировки). Ниже уже актуальная версия:

```
/                                        главная
/grooming/bratislava/                    груминг по городу
/grooming/bratislava/{district}/         груминг по району
/vet-clinics/bratislava/                 ветклиники по городу
/vet-clinics/bratislava/{district}/
/pet-hotels/bratislava/                  отели/передержка
/pet-hotels/bratislava/{district}/
/dog-training/bratislava/                дрессировка
/pet-shops/bratislava/                   зоомагазины
/pet-sitting/bratislava/                 выгул/ситтинг на дому
/business/{slug}/                        карточка конкретного бизнеса
/how-it-works/
/add-or-fix-listing/
/privacy-policy/
/terms-of-use/
/blog/{slug}/                            P1, не в MVP
```

Категории — по одному URL-сегменту на категорию, а не общий
`/services/{category}/`, потому что это ближе к тому, как реально
ищут в Google («vet clinic Bratislava», а не «pet services Bratislava
vet»), и совпадает с `docs/ux-flow.md` (SEO-страница услуги — основной
вход, не флоу с главной).

Слаги подтверждены исследованием (см. раздел 3 выше) — можно
реализовывать как финальные, без ожидания дальнейших правок.

Правило индексации (уже есть в `docs/concept.md`, повторяю явно):
страница района/категории получает `index` только если на ней ≥ 3
опубликованных бизнеса, иначе `noindex` и не в sitemap.

`bratislava` в путях выше — единственный город на старте, но это
**данные, не константа в коде**: реализуется как динамический сегмент
`[city]` (не литеральная папка), см. раздел 2.2 — при добавлении
следующего города эти же пути автоматически работают с новым слагом
города, без правок кода.

## 4. Инвентарь страниц

### 4.1 Главная (`/`)
Уже частично реализована. Владелец отдельно отметил, что мобильная
версия поиска на Zocdoc «выглядит круто» и хочет такой же уровень —
детальный разбор этого паттерна уже есть в
`docs/research/interface-references.md` (раздел 1.1), уточняю здесь,
что именно взять:

- Тап по полю поиска открывает **полноэкранный оверлей** с фокусом на
  инпуте (а не просто разворачивает список на месте) и списком
  популярных запросов ниже (например, «Grooming in Petržalka», «Vet
  clinics near me») — это и есть тот самый «крутой» эффект Zocdoc, не
  просто стилизация цветом.
- Оверлей закрывается свайпом вниз или крестиком, без перезагрузки
  страницы.
- Это относится к шагам 2-3 флоу ниже (выбор услуги/района) — на
  мобильном они реализуются как этот оверлей, а не только как плоские
  карточки-кнопки, как сейчас в `website/app/page.tsx`.

Блоки (по порядку):
1. Hero: заголовок + подзаголовок (есть).
2. Поиск — на мобильном 3 карточки-шага (животное → категория →
   район), но выбор услуги/района открывает полноэкранный оверлей (см.
   выше), на десктопе — комбинированная строка (3 select + кнопка),
   уже есть в вёрстке, но пока не подключена к реальному переходу
   (селекты ничего не делают при сабмите) — доделать submit → редирект
   на `/{category}/bratislava/?animal=...&district=...`.
3. Статистика (счётчики по категориям) — сейчас считает из CSV
   напрямую, после `cli-generalize-business-model-and-seed` должен
   считать из БД.
4. Блок «как это работает» — короткий тизер + ссылка на
   `/how-it-works/`.
5. Ссылка «добавить/исправить бизнес» → `/add-or-fix-listing/`.
6. Footer со ссылками на все категории (для внутренней перелинковки —
   `docs/ux-flow.md`, «hub-страницы»).

### 4.2 Категория × город (`/{category}/bratislava/`)
Цель: ответ на запрос вида «vet clinic Bratislava».
Блоки:
- H1 с запросом («Veterinary clinics in Bratislava»).
- Панель фильтров: район (17 slug'ов из `docs/concept.md` Приложение
  B), вид животного (dog/cat), диапазон цены (только если у категории
  есть хоть одна запись в `PriceItem` — иначе фильтр не показываем,
  не выдумываем пустую функциональность).
- Сортировка: по цене (если есть данные), по расстоянию (если
  разрешена геолокация И у бизнесов есть lat/lng — до задачи
  `antigravity-geocode-listings` эта опция скрыта, не сломана
  показом координат 0,0), по умолчанию — фиксированная ежедневная
  псевдослучайная ротация (равные шансы, без реальной случайности при
  каждом рендере — иначе SSG-страница будет мигать при каждой
  генерации).
- Мобильный фильтр-бар — горизонтальный скролл чипсов (район,
  «Открыто сейчас» — только если у категории есть `openingHours`
  хотя бы у части бизнесов, «Цена» — только если есть `PriceItem`),
  по референсу Zocdoc/Yelp из `docs/research/interface-references.md`
  раздел 5, вместо тяжёлой боковой панели фильтров на мобильном.
- Список карточек бизнесов (см. 5.2).
- Короткий поясняющий текст про категорию в городе (1-2 абзаца,
  человеческим языком, без маркетингового пафоса — из `PRODUCT.md`).
- FAQ-блок (2-4 вопроса, специфичных для категории) — контент
  подготовить позже отдельной задачей, не блокирует вёрстку (можно
  показывать секцию только когда есть контент).
- Блок «ещё рядом»: ссылки на соседние категории в том же городе и на
  районные под-страницы этой категории.

**Осознанно не делаем сейчас:** плавающую кнопку-переключатель
`Map / List` с Zocdoc (`docs/research/interface-references.md`,
1.1/1.5) — она предполагает существование карты, а встроенная карта
(MapLibre) не в P0 (раздел 6 ниже). Добавляем оба вместе, когда дойдём
до карты, не раньше — переключатель без карты бессмысленен.

### 4.3 Категория × город × район (`/{category}/bratislava/{district}/`)
То же самое, что 4.2, но отфильтровано по одному району. Возвращает
`noindex`, если < 3 бизнесов в этом районе с `status: PUBLISHED`.

### 4.4 Карточка бизнеса (`/business/{slug}/`)
Цель: решение и контакт за один экран.
Блоки:
- Название (h1), категория, бейдж «Verified: {дата}» (если
  `verifiedAt` есть), бейдж «Partner» (если `featured: true` — сейчас
  всегда false, зарезервировано на будущее, не показывать пустой
  бейдж), рейтинг (среднее по `PUBLISHED` отзывам + число отзывов) —
  только если есть хотя бы один опубликованный отзыв (раздел 2.1).
- Адрес + район, карта — заглушка/статичная ссылка на OSM/Google Maps
  по адресу, встроенная карта (MapLibre) — не в P0, `docs/concept.md`
  раздел 13 относит карты отдельным пунктом; для MVP достаточно
  текстового адреса + ссылки «маршрут».
- Три кнопки быстрого действия: «Call» (`tel:`), «Website» (новая
  вкладка), «Route» (ссылка на карты) — из `docs/concept.md` раздел 8,
  минимум 44×44px на мобильном (`docs/ux-flow.md`).
- Виды животных, специализации (pills).
- Галерея фото — только если у бизнеса есть `photoUrls` (в MVP,
  вероятнее всего, пусто у всех — см. раздел 2.1 про ограничение на
  права на фото); блок не рендерится вообще, если массив пуст.
- Таблица цен — **только если есть хотя бы одна строка `PriceItem`**
  для этого бизнеса; если данных нет, блок не рендерится вообще (не
  «Price: N/A» — просто нет блока, честнее).
- Часы работы — если есть `openingHours`, иначе не показываем.
- **Отзывы** (раздел 2.1): список `PUBLISHED` отзывов (имя автора,
  оценка звёздами, текст, дата) + форма «Оставить отзыв» (имя, оценка
  1-5, текст) ниже списка. Отправленный отзыв уходит со статусом
  `PENDING` и сразу не появляется в списке — на форме сразу после
  отправки показать «Спасибо, отзыв появится после проверки», не
  делать вид, что он опубликован.
- Футер карточки: «Info verified: {observedAt/verifiedAt}, source:
  {sourceUrl}» + ссылка «Report an issue» (`mailto:` на адрес
  владельца, без формы в MVP — форма `add-or-fix-listing` общая, не
  дублировать).
- JSON-LD: `LocalBusiness` (или подтип в зависимости от категории),
  `BreadcrumbList`, `AggregateRating` — только при наличии
  опубликованных отзывов (структурированные данные о рейтинге без
  реальных отзывов — это как раз тот фиктивный сигнал, который Google
  наказывает, и который прямо противоречит «не выдумывать факты»).

#### Сводка отзывов «Что говорят клиенты» (решение владельца 2026-09-24)

Данные: `data/review-insights/<slug>.json` (задача
`docs/playbooks/review-insights.md`): 3 тематические карточки + 3-6 FAQ,
EN/SK, по отзывам Google за последние 6 месяцев. Правила показа:

- Заголовок блока: «What customers say» / «Čo hovoria zákazníci»,
  подзаголовок: «pawenn summary of {N} Google reviews from {period}» /
  «Zhrnutie pawenn z {N} recenzií na Google za {obdobie}» + ссылка
  «All reviews on Google» / «Všetky recenzie na Google»
  (`google_maps_url`, `rel="nofollow noopener"`, новая вкладка).
- Карточки — **не в виде отзывов**: без аватаров, имён, звёзд на
  карточке. Тема + метка тональности (positive/mixed/negative) +
  «{mentions} z {N} recenzií».
- Строка-раскрытие под блоком (Omnibus): «Súhrn verejných recenzií z
  Google, pawenn ich neoverujeme.» / «Summary of public Google reviews;
  pawenn does not verify them.»
- **Никакой разметки `Review`/`AggregateRating`** для этого блока и
  для рейтинга Google (правила Google запрещают размечать чужие
  отзывы). Разрешено: `FAQPage` JSON-LD для FAQ — это наш контент.
- Язык — по языку страницы (`/sk/` — `sk`, `/en/` — `en`), без
  подстановки другого языка.
- Нет файла или ему больше 7 месяцев (`observed_at`) — блок не
  показывать.

## 5. Компоненты (переиспользуемые)

- `Header` — лого, ссылки на 6 категорий, ссылка «How it works».
- `Footer` — те же ссылки + Privacy/Terms + copyright.
- `Breadcrumbs` — по иерархии город → категория → район → бизнес.
- `SearchBar` — две реализации в одном компоненте: mobile (карточки-шаги) и desktop (строка с 3 select), общая логика сборки URL при сабмите.
- `FilterPanel` — район/животное/цена, рендерит только доступные для текущей категории фильтры (не показывать фильтр по цене, если у категории нет ни одной цены в БД).

- `VerifiedBadge`, `PartnerBadge` — маленькие переиспользуемые бейджи.
- `QuickActions` — три кнопки Call/Website/Route, общие для карточки списка и страницы бизнеса.
- `EmptyState` — когда после фильтра 0 результатов: «Ничего не найдено» + ссылка сбросить фильтр (не путать с `noindex`-страницами — это разные вещи: пустой результат фильтра на реальной странице с контентом vs. страница без данных вообще).

### 5.2 Карточка бизнеса в списке (`BusinessCard`)
Референс по раскладке — Zocdoc/Yelp (`docs/research/interface-references.md`,
разделы 1.2, 3.2): фото/аватар слева, метаданные справа.
- Фото/аватар (64×64px мобильный, 80×80px десктоп) — если есть
  `photoUrls[0]`, иначе — нейтральная заглушка-иконка по категории
  (не пустое место и не чужое фото).

- Рейтинг + число отзывов («4.8 (12)») — только если есть хотя бы
  один `PUBLISHED` отзыв (раздел 2.1); нет отзывов — нет строки.

- Цена «от €X» — только если есть `PriceItem`, иначе не показывать
  строку вообще (см. правило из 4.4).
- `QuickActions` (Call/Website/Route).
- `VerifiedBadge`, если применимо.
- Клик по карточке → переход на `/business/{slug}/` (не
  раскрытие на месте — по `docs/ux-flow.md`, решение принято в пользу
  отдельной страницы ради SEO: у каждой карточки должен быть

## 8. GEO/AEO: видимость в LLM-ассистентах (ChatGPT/Claude/Gemini/Perplexity)

Решение владельца (2026-09-21): готовить сайт к тому, чтобы
браузинг-ассистенты (ChatGPT с поиском, Claude с web search, Gemini с
Search grounding, Perplexity и т.п.) могли находить и цитировать наши
страницы в ответах — до масштабирования на новые города, чтобы это
работало по шаблону, а не докручивалось на каждый город вручную.

**Честная рамка ожиданий:** это не отдельный канал с особыми рычагами
— технически почти полностью пересекается с обычным SEO, потому что
браузинг-ассистенты по большей части берут результат из тех же
поисковых индексов (в первую очередь Bing, отчасти Google), что и
обычный поиск. Модели без браузинга (офлайн-знания с cutoff) в
принципе не увидят маленький локальный сайт, пока он не попал в
обучающую выборку — на это повлиять нельзя, это не цель. Реалистичная
задача — максимизировать шанс попасть в ответ там, где движок реально
ходит в веб, а не гарантировать цитирование.

Что конкретно закладываем в шаблон (один раз на категорию/схему, не
на город — переиспользуется при масштабировании):

1. **Явный допуск AI-краулеров в `robots.txt`** — `GPTBot`, `ClaudeBot`/
   `anthropic-ai`, `Google-Extended`, `PerplexityBot`, `CCBot` и т.п. не
   должны быть заблокированы (по умолчанию некоторые сайты блокируют
   их от копирования контента — нам нужно обратное).
2. **`JSON-LD` расширяется, не только `LocalBusiness`/`BreadcrumbList`/
   `AggregateRating`** (уже в объёме `cli-build-listing-and-detail-pages`):
   добавить `dateModified` от `verifiedAt` (сигнал свежести для
   ответных систем) и `FAQPage` со списком частых вопросов.
3. **FAQ-блок на странице категория×город, сгенерированный из данных,
   а не написанный руками на город** — шаблон вопросов на уровне
   категории («Сколько стоит {категория} в {город}?», «Какие
   {категория} в {район} работают без предварительной записи?» и
   т.п.), ответы подставляются из реальных агрегатов (диапазон цен из
   `PriceItem`, количество заведений, доля с `verifiedAt`) — при
   добавлении города работает автоматически, без ручного текста.
4. **`/llms.txt`** — неформальный, ещё не универсально принятый
   стандарт (аналог `robots.txt`/`sitemap.xml`, но для LLM): короткое
   машиночитаемое описание сайта + ссылки на ключевые страницы
   (главная, все 6 категорий, `/how-it-works/`). Стоит копейки,
   форматируется по тому же шаблону категорий, что и всё остальное.
5. **Bing Webmaster Tools** — отдельно от Google Search Console (уже
   упомянут в `docs/concept.md`), т.к. Bing-индекс питает Copilot и
   часть ChatGPT-поиска. Это не код, а ручной шаг после первого
   деплоя (нужен живой домен) — не задача ни для одного агента прямо
   сейчас, зафиксировать как шаг на этапе деплоя (Sprint, раздел T0.4
   `docs/concept.md`).
