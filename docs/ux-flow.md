# UX-флоу сайта (черновик, дорабатываем итеративно)

**Статус:** живой документ. Не финальный макет, а структура — что
происходит на каждом шаге и почему, без привязки к пиксельному дизайну.
Обновляется по мере обсуждения с владельцем проекта.

Соотносится с `docs/concept.md`: там — SEO/URL-архитектура и блоки
страниц (разделы 4-5, 8), здесь — **путь пользователя, который зашёл
на главную и ещё ничего не искал**. Это разные вещи, которые должны
согласовываться по смыслу: SEO-страница — это уже готовое
"приземление" из поиска (человек гуглит «груминг салон Братислава» и
сразу попадает на отфильтрованную страницу услуги), а флоу ниже — это
навигация внутри сайта для тех, кто зашёл на главную напрямую.

## Референс и общий стиль

- Интерфейс в духе **TripAdvisor**: карточки, списки, рейтинги,
  browse-first — человек листает и сравнивает, а не заполняет форму.
- **Mobile-first в первую очередь**, но должно нормально работать и на
  десктопе. Основной сценарий: человек гуглит с телефона конкретный
  запрос («груминг салон Братислава») и хочет решение за 2-3 клика.
- Многостраничный сайт — у каждого пересечения город × услуга (×
  порода) уже есть отдельная проиндексированная страница по
  `docs/concept.md` (раздел 4). Флоу ниже — это то, как до такой
  страницы дойти, если зайти не из поиска, а с главной.

## Что показал внешний ресёрч (аналоги)

Смотрел на паттерны Zocdoc (specialty → insurance → location →
список врачей), TripAdvisor и общую практику программного SEO для
директорий (category/city URL-структуры). Три вывода, которые меняют
акценты в флоу ниже:

1. **Реальный трафик приходит не через флоу с главной, а напрямую на
   SEO-страницу услуги.** У директорий вроде TripAdvisor/Zocdoc
   основной вход — это Google-запрос, который сразу приземляет на
   готовую отфильтрованную страницу (category+city), а не на главную.
   Это подтверждает то, что уже заложено в `docs/concept.md` (раздел
   4): **URL-структура и SEO-страницы — это первично**, флоу с главной
   ниже — это вторичный, дополнительный путь для прямых заходов и
   повторных визитов, а не основной канал роста.
2. **У успешных директорий поиск и категории — не «либо/либо», а
   работают параллельно с самого начала.** Zocdoc даёт one-shot строку
   поиска (специальность/симптом + локация + страховка сразу), а не
   заставляет линейно щёлкать по 3 экранам подряд. Карточки-шаги — это
   вариант для тех, кто не знает точный запрос, но строка поиска
   должна быть равноценным, а не второстепенным путём.
3. **Внутренняя перелинковка через hub-страницы** — общая практика
   программного SEO: главная (или отдельная hub-страница) линкует на
   все страницы города/района, страницы услуг линкуют на смежные
   услуги и соседние районы. Стоит заложить это в шаблон страницы
   сразу, а не добавлять потом.

Практический вывод для мобильного интерфейса (тоже из ресёрча):
кнопки быстрого действия (звонок и т.п.) должны быть не меньше 44×44px
и с фиксированным позиционированием на мобильном — это уже совпадает
с `docs/concept.md` (раздел 8, кнопки «Zavolať/Web/Trasa»), но стоит
явно занести как техническое требование к вёрстке карточки.

## Флоу с главной страницы: 3 шага

**Шаг 0 (равноценно шагам ниже, не «запасной путь»).** Наверху главной
— поисковая строка, как у обычного поисковика, с автодополнением по
паре «животное + услуга» (например, «стрижка собак»). Это не для
«продвинутых» пользователей отдельно от карточек — судя по аналогам,
это должен быть основной путь наравне с карточками, а не второстепенный.

**Шаг 1 — тип питомца.** Карточки: Собака, Кошка (в MVP — только эти
два, согласно `docs/concept.md` раздел 3 и 8; остальные виды — позже).

**Шаг 2 — тип услуги.** После выбора животного — карточки актуальных
для него услуг: Ветклиника, Груминг-салон, Отель/передержка (дальше —
зоомагазин, дрессировка и т.д., по мере того как эти категории данных
появляются — см. `data/other-pet-services-bratislava.csv`).

**Шаг 3 — локация.** Пользователь либо вводит город, либо — лучше —
сайт спрашивает разрешение на геолокацию и сам предлагает «рядом с
вами», используя её для сортировки по расстоянию (эта возможность уже
заложена в `docs/concept.md` раздел 8, «Сортировка... если пользователь
разрешил геолокацию»).

**Результат.** Список карточек: фото/заглушка, название, цена «от»,
2-3 ключевых атрибута, кнопки быстрого действия (звонок/сайт/маршрут —
уже описано в `docs/concept.md` разделе 8).

## Решения по ходу (можно пересматривать, но чтобы не топтаться на месте)

- **Отдельные разделы вроде «рейтинг кормов»** — не часть 3-шагового
  флоу услуг, а отдельный пункт верхнего уровня (ближе к блогу/сравнению,
  не к «найти услугу рядом со мной»). Причина: логика поиска услуги и
  логика сравнения товаров — разные сценарии использования, смешивать
  их в один флоу усложнит оба.
- **Шаг 3 (город) в MVP можно пропустить визуально**, раз город всегда
  один (Братислава) — сразу переходить от шага 2 к результатам. Поле
  выбора города появляется, когда добавится второй город.
- **Порядок шагов зафиксирован:** животное → услуга → локация. Это
  совпадает с иерархией `docs/concept.md` (город → район → услуга →
  порода → салон), где услуга и порода/вид животного всегда конкретнее
  города — так URL-структура и флоу навигации не расходятся.

## Что здесь намеренно не решено

- Точный визуальный макет (расположение, размеры карточек, цвета) —
  это отдельный этап, не этот документ. Здесь только структура шагов.
- Как именно проектировать переход «карточка услуги → страница
  результатов» технически (отдельная страница vs. модалка/раскрытие на
  месте) — решить при вёрстке, ориентируясь на скорость (Core Web
  Vitals, `docs/concept.md` раздел 11).
