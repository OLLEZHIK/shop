# База данных — решение и как подключиться

## Решение: Neon (через Vercel Storage), регион Frankfurt

**С 2026-09-24 боевая база — Neon, бесплатный тариф.** Раньше был
Prisma Postgres (project `proj_uhvlbpwgi0bvk3ewj9cky9xr`, database
`db_u1lby7vqe8bru1uh74q3ep7f`), но его бесплатный тариф считает каждую
операцию (100 000 в месяц). Лимит закончился, и все страницы, которые
читают базу, стали отдавать 500 (P6003). У Neon лимит по времени работы
базы, а не по числу запросов, и для MVP этого хватает. Старая база
осталась нетронутой как запасная копия: данные в ней и в Neon одинаковые,
потому что обе заполнены из одних и тех же CSV.

Кроме того, чтения из базы кэшируются на сутки (`website/lib/data.ts`,
`unstable_cache`), так что к базе обращается примерно одна страница
в сутки, а не каждый просмотр.

## Откуда приложение берёт подключение

Всё решает `website/prisma/db-url.ts`:
- **На Vercel** Neon подключён через Storage, и его переменные
  окружения появляются в проекте автоматически. Код ищет их по хосту
  `*.neon.tech`, а не по имени переменной, поэтому префикс,
  выбранный при подключении, неважен. Приложение использует пулованное
  подключение (`-pooler` в хосте), миграции и seed — прямое.
- **Локально** (Neon-переменных нет) берутся `DATABASE_URL` /
  `DIRECT_URL` из `website/.env.local`. Обе должны быть обычными
  `postgres://` строками.

## Локальная разработка — только на своей базе

**Не подключайтесь локально к боевой базе.** Любой локальный запуск
тратит её ресурсы, и из-за этого мы уже однажды положили сайт. Поднимите
локальный Postgres (например, `docker run -p 5432:5432 -e
POSTGRES_PASSWORD=postgres postgres:16`) и в `website/.env.local`
пропишите:

```
DATABASE_URL="postgres://postgres:postgres@localhost:5432/pawenn"
DIRECT_URL="postgres://postgres:postgres@localhost:5432/pawenn"
```

Затем в `website/`: `npx prisma migrate deploy && npm run db:seed`.

## Миграции и seed на Vercel

`npm run build` сначала запускает `website/scripts/db-setup.ts`:
- **Любая сборка на Vercel** применяет новые миграции
  (`prisma migrate deploy`): новому коду нужны его колонки уже при
  сборке.
- **Seed** запускается только на новой пустой базе и в production-сборке.
  Так изменения CSV после мерджа попадают на сайт, а незамёрженный PR
  боевые данные не меняет.
- **Локальная сборка:** ничего не трогает.

**Правило для миграций: только добавлять.** Новые таблицы и колонки
допускающие NULL — можно. Удалять и переименовывать в том же изменении
— нельзя. Причина: превью-сборка PR может работать на той же базе, что
и боевой сайт, и применит миграцию до мерджа. Добавление старому коду
не мешает, а удаление сломало бы работающий сайт. Удаление делается
отдельным PR, когда код уже не использует колонку.

Seed (`website/prisma/seed.ts`) делает upsert по slug, его можно
запускать повторно. Данные о заведениях живут в CSV — это источник
правды, база из них пересобирается:

- **`data/cities/<город>/`** (`docs/playbooks/add-city.md`):
  - `city.json` → город;
  - `districts.geojson` → районы;
  - все `businesses*.csv` → заведения, slug берётся из столбца `slug`,
    одинаковый slug в двух городах останавливает seed с ошибкой;
  - `prices.csv` → цены, заменяются целиком;
  - `review-insights/<slug>.json` → сводка отзывов.
- **Район заведения** определяется по `lat`/`lng` и полигонам из
  `districts.geojson`. Полигоны скачивает
  `website/scripts/fetch-districts.ts <город> <OSM relation> [admin_level]`,
  результат коммитится. Seed в сеть не ходит.
- **Братислава** с 2026-09-25 тоже в `data/cities/bratislava/`. Старый
  путь из `data/*-bratislava.csv` в seed остаётся, только пока старые
  файлы не удалены (`data/cities/bratislava/README.md`).
- **Итог по городам** печатается в конце: сколько заведений, районов,
  часов работы, цен, сводок отзывов. Там же предупреждения: неверные
  часы, неизвестные коды, логотип не найден.
- **Проверка на выдуманном городе:** `website/prisma/fixtures/README.md`.
  Только на отдельной локальной базе.

## Вместимость бесплатного тарифа Neon (расчёт 2026-09-24)

- **Размер строки заведения.** Сейчас в среднем 380 байт (максимум 531),
  замер на боевых данных. С описаниями, рейтингом, логотипом и
  сводкой отзывов — около 1,5 КБ. Вместе с индексами и служебным
  местом Postgres закладываем **~3 КБ на заведение**.
- **Город со 100 заведениями ≈ 0,3 МБ.** Районы весят копейки.
- **База сейчас весит ~8 МБ.** Лимит бесплатного Neon — 0,5 ГБ на
  проект. Если оставить ~100 МБ запаса под отзывы и клики,
  получается **около 1 300 городов**.
- **Клики и отзывы растут с трафиком:** клик ~100 байт, 10 000 кликов
  ≈ 1 МБ.

Место в базе закончится последним. Раньше упрёмся в другие вещи, и
их нужно доработать до ~10–20 городов:
- **Сборка сайта.** Каждый город добавляет примерно 6 категорий ×
  (1 + число районов) × число языков страниц, которые собираются
  заранее. Братислава — около 230 страниц. На десятках городов сборка
  станет очень долгой (на Vercel Hobby сборка ограничена 45 минутами).
  Решение: страницы городов рендерить по запросу с кэшем, а не
  собирать все заранее.
- **Seed при сборке.** Одна запись из сборки Vercel (США) в Neon
  (Франкфурт) — ~0,1 с. 10 000 записей по одной — это минуты сборки.
  Решение: пакетная запись и загрузка только изменившихся городов.
- **Рейтинги через Google Places API.** 100 городов × 100 мест =
  10 000 запросов на одно обновление. После бесплатной 1 000 в месяц —
  около $20 за 1 000, то есть ~$180 за обновление всех. Решение
  владельца нужно до масштабирования.
- **Время работы базы (100 CU-часов в месяц).** С суточным кэшем на
  сотнях городов при умеренном трафике хватает.
